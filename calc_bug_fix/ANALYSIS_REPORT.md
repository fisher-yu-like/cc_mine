# 上下文压缩管道深度分析

## 模拟结果

```
场景            原始tok    压缩后tok   保留率   冻结   剪除   预估重做   是否摘要
──────────────────────────────────────────────────────────────────────────
短对话(10轮)      3,382      3,382    100%      0     -1        0      否
中等对话(25轮)     6,532      1,482     23%      3     24    7,500      否
长对话(40轮)      47,336      5,006     11%      6     69        0      否
```

## 四个核心问题

### 1. snip_compact 是最致命的

- 25轮对话：**丢失24条中段消息**（9 tool + 8 assistant + 9 user）
- 40轮对话：**丢失69条中段消息**（24 tool + 23 assistant + 24 user）
- 只保留 head 3 + tail 47
- head 3 = system prompt + 第一条 user + 第一条 assistant → **几乎零信息量**
- 中间的代码探索、错误分析、修复尝试 → **全部消失**

### 2. micro_compact 主动引导浪费

被冻结的工具结果被替换为：
```
[Earlier tool result compacted by system, Re-run command if needed.]
```

这**直接引导 LLM 重新执行命令**。3个被冻结的 read_file = ~7,500 tokens 重做成本。

场景2中：节省了 5,050 tokens，但重做成本 7,500 tokens → **净浪费 +2,450 tokens**

### 3. prepare_context 每轮都执行（持续伤害）

```python
# main.py line 66 — 在 while True 循环内
prepare_context(messages)  # 每轮都执行！
```

对话越长，被 snipped/micro-compacted 的消息越多，信息损失呈**线性累积**。

### 4. compact_history 永远不会触发

前三层（budget + snip + micro）把上下文压得太狠了。
场景3中 196KB → 24KB，远低于 CONTEXT_LIMIT (50000 tokens)。
结果：**暴力删除信息，却不使用智能摘要**。

## 净损失模型

```
净收益 = 压缩节省的tokens - 重做浪费的tokens

短对话:    0 - 0 =      0  (无影响)
中等对话:  5,050 - 7,500 = -2,450  (亏损!)
长对话:    42,330 - 15,000 = +27,330 (表面盈利，但丢失了大量探索上下文)

注意：长对话的"盈利"是假象——丢失的69条消息中包含关键的探索和推理，
LLM会在后续对话中逐渐暴露出信息缺失，导致间接重做。
```

## 根本原因

四层压缩的设计假设是：
1. 旧信息不重要 → 直接丢弃
2. LLM 需要的信息总在最近的 tool results 里
3. 暴力删除优于智能摘要

但实际情况是：
1. 旧信息可能包含关键的探索结论（"已确认bug不在A模块"）
2. LLM 经常需要引用早期的分析结果
3. 用 flash 小模型做摘要比暴力删除更省 token
